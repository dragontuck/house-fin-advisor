# AI Financial Advisor
## Product, Development & Vibe-Coding Master Plan

**Purpose:** Build a privacy-first, self-hosted household financial intelligence platform that provides researched, challengeable financial guidance through a simple conversational experience.

**Primary deployment model:** Docker / Docker Compose, self-hosted.

**Primary users:** Two-person household; both spouses have first-class identities and access to shared household financial information.

**Core principle:** The product is a financial decision platform with an AI interface—not an LLM with access to raw financial data.

---

# 1. Product Vision

The AI Financial Advisor should become a **household financial operating system** that continuously understands the household's current financial state and helps answer questions such as:

- How are we doing financially?
- Help me create an initial budget.
- Why am I always over budget?
- Help me revise the budget for next month with these known activities.
- Can we afford this?
- What should we do with this unexpected expense?
- What should we do with this unexpected money?
- Which credit card should I use?
- Are our savings goals on track?
- Are we on track for financial independence?

The system should remember the household's structured financial state so the user does not have to restate it in every conversation.

The system should also make it easy for a non-technical spouse to:

- connect financial accounts;
- upload statements;
- resolve an error;
- understand the household's financial position;
- understand why a recommendation was made;
- approve or reject a proposed financial plan.

# 2. Core Architectural Principles

## 2.1 Financial truth is deterministic

Balances, budgets, cash flow, debt, goal progress, scenario calculations, financial independence projections, and other material calculations must be produced by deterministic application services—not generated by the LLM.

## 2.2 The LLM is a reasoning and communication interface

The AI should:

- understand natural language;
- select approved tools;
- explain structured financial results;
- compare alternatives;
- manage conversational context;
- assist with planning workflows;
- summarize validated research.

The AI should not be the system of record.

## 2.3 Minimum data exposure

Raw financial records remain inside the self-hosted environment by default.

External LLM calls must pass through a privacy gateway that:

- minimizes context;
- removes restricted identifiers;
- blocks secrets;
- prevents raw statement leakage;
- allowlists external destinations.

## 2.4 Tool-only AI access

The AI must never receive unrestricted database, filesystem, shell, or network access.

All financial access occurs through typed, authorization-aware tools.

## 2.5 Explainability

Material financial outputs should distinguish:

- Fact
- Calculation
- Assumption
- Analysis
- Proposal
- Approved decision

## 2.6 Explicit approval

The AI can propose a budget, allocation, scenario, or other plan, but it cannot silently change household financial state.

## 2.7 Exceptions instead of perfection

Normal processing should be automated. Ambiguity should move to a Review Queue instead of forcing the whole workflow to fail.

## 2.8 UX simplicity

The default UI should be understandable by a non-technical spouse without understanding:

- APIs;
- OCR;
- bank aggregation;
- reconciliation;
- AI orchestration;
- Docker;
- cloud infrastructure.

# 4. Development Strategy

## 4.1 Use vertical slices

Do not build the application strictly by technical layer.

Each slice should produce a working user-visible capability.

```text
Slice
  ↓
Domain capability
  ↓
API capability
  ↓
UI capability
  ↓
Tests
  ↓
UX validation
  ↓
Architecture review
```

## 4.2 Use a modular monolith first

The target architecture contains logical service boundaries, but the rapid prototype should not begin as a collection of 15 microservices.

Start with approximately:

```text
web
api
worker
postgres
redis
minio
keycloak
reverse-proxy
```

Maintain logical modules so they can later be extracted:

```text
api/modules/
  household
  accounts
  transactions
  statements
  reconciliation
  budgets
  goals
  financial-intelligence
  advisor
  recommendations
  research
  validation
```

## 4.3 One large prompt + targeted prompts

For every slice use:

1. One **slice-scoping/master prompt** that establishes the objective, boundaries, architecture, UX expectations, and definition of done.
2. Several **targeted prompts**, each implementing one coherent capability.
3. One **integration prompt**.
4. One **architecture / financial correctness / security / UX review prompt**.
5. Targeted repair prompts for selected review findings.

Do not use one huge prompt to build an entire slice.

## 4.4 Coding-agent operating rule

The agent should optimize for preserving architecture while completing the current slice—not simply for completing the current prompt.

# 18. AI Persona Selection Feature

## Objective

Allow the household user to choose an **AI advisor persona** that influences the style, emphasis, questions, and framework used when presenting advice.

### Critical design rule

These personas should be treated as **named advisory styles/frameworks**, not as impersonations of real people or representations that the named person/organization endorses the application.

The system should never imply:

- the real person is providing the answer;
- the real organization reviewed the household finances;
- the person endorsed the product;
- proprietary/private prompts from those individuals or organizations are being used unless legitimately licensed or sourced.

Use persona labels such as:

> "Kitces-inspired retirement planning framework"

or, if the user chooses the exact supplied label:

> "Michael Kitces — retirement planning emphasis"

with an unobtrusive notice:

> "This is an AI advisory style inspired by publicly described areas of expertise. It is not the real person or organization."

- id
- name
- shortDescription
- planningFocus
- communicationStyle
- questionStyle
- analysisPriorities
- cautionAreas

- systemBehaviorRules
- version
- enabled

The persona must never change:

# 27. Definition of Done for the Entire Product

The system is directionally complete when:

1. Both spouses can use the application without technical assistance.
2. The household financial state is continuously current.
3. Statements can be uploaded with minimal user effort.
4. Normal ingestion is automatic.
5. Ambiguity goes to a clear Review Queue.
6. The dashboard explains household financial health in seconds.
7. The AI automatically retrieves relevant current financial context.
8. Budget creation is conversational and guided.
9. Budget diagnosis distinguishes behavior from an unrealistic budget.
10. Next-month budget planning supports known activities and conversational constraints.
11. Recommendations are evidence-backed and independently challenged.
12. Current facts are sourced and timestamped.
13. Public LLM access is minimized and privacy-controlled.
14. The application remains useful when external AI is unavailable.
15. Persona selection changes framing but never financial truth.
16. Financial decisions are auditable.
17. Budget and financial-state changes require explicit approval.
18. Backups can be restored and tested.
19. Financial calculations have deterministic regression scenarios.
20. The application can be reproduced entirely from Docker-based deployment artifacts.

# 28. Recommended First Coding Session

Do not begin by implementing the full target architecture.

Start with:

```text
1. Initialize repository
2. Create AGENTS.md
3. Create PRODUCT_BUILD_CONTRACT.md
4. Create Docker Compose baseline
5. Create web/api/worker shells
6. Create PostgreSQL
7. Create Keycloak
8. Establish Money primitive
9. Implement Slice 1 domain
10. Seed a fictional household
11. Build FinancialSnapshot
12. Build Financial Pulse
13. Run first spouse usability test
```

The first meaningful milestone is not:

> "The AI works."

It is:

> "A household can open the application and understand its current financial situation within 30 seconds."

The next milestone is:

> "A spouse can drop in a statement and the system handles almost everything automatically."

Then:

> "I can ask the advisor a question without explaining my finances."

Then:

> "The advisor can help us create and revise our budget conversationally."

Then:

> "The advisor can research, challenge, and explain a financial recommendation."

That progression keeps the prototype fast while preserving the architecture needed for a serious privacy-first household financial advisor.
