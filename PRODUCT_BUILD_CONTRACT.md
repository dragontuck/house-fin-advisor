## 1. Core Product Principles

### 1.1 Financial Truth is Deterministic
- All balances, budgets, cash flow, debt, goal progress, scenario calculations must be produced by deterministic domain services, not generated by the LLM
- Financial calculations never occur in prompts, controller logic, or UI code
- Every derived financial value has `calculation_version`, `calculated_at`, and `source_snapshot_id`
- Domain services own all financial rules
- No duplication of business rules across UI and backend

### 1.2 The LLM is a Reasoning and Communication Interface
- The AI understands natural language and selects approved tools only
- The AI explains structured financial results, compares alternatives, and manages conversational context
- The AI is never the system of record for financial state
- The AI **cannot**: invent balances, rates, transactions, claim research it didn't perform, or make money transfers
- Tool-only access: the AI never receives unrestricted database, filesystem, shell, or network access

### 1.3 Minimum Data Exposure
- Raw financial records remain inside the self-hosted environment by default
- External LLM calls must pass through the privacy gateway that:
  - Minimizes context
  - Removes restricted identifiers (SSN, account numbers, routing numbers, credentials, card numbers, raw statements)
  - Blocks secrets
  - Prevents raw statement leakage
  - Allowlists external destinations
- Anthropic is the only currently implemented external provider

### 1.4 Recommendations are Structured, Typed, and Governed
- Every recommendation reference includes `financial_snapshot_id`, `policy_version`, `evidence`, and `validation_result`
- Recommendations are created through a deterministic pipeline: scenario building → candidate generation → validation → selection
- The LLM proposes; it does not approve or execute financial state changes
- Invalid recommendations (failed validation) are not delivered; instead, an explanatory failure is returned
- Recommendations expire automatically when snapshot or policy versions change
- All alternatives, assumptions, and risks are returned from the domain layer, never synthesized in the UI

### 1.5 Explainability and Auditability
- Material financial outputs distinguish: Fact, Calculation, Assumption, Analysis, Proposal, Approved Decision
- Every recommendation is persisted before delivery with complete lineage: question → financial context → tool outputs → scenarios → evidence → validation → recommendation
- Decision journals record each pipeline stage with timestamps and inputs/outputs
- Historical recommendations can be reproduced from saved journal entries
- Personas affect presentation only, not calculations
- No impersonation language is used; all personas include fictionalization disclaimer

### 1.6 Explicit Approval
- The AI can propose a budget, allocation, scenario, or plan, but **cannot** silently change household financial state
- State changes require explicit approval
- Approval status is separate from recommendation validity
- Approval history is append-only and auditable

### 1.7 UX Simplicity
- The default interface must be understandable by a non-technical spouse within 30 seconds without understanding APIs, OCR, bank aggregation, or Docker
- Never expose: stack traces, database errors, OAuth errors, provider error codes, implementation details
- Every error explains: What happened, Why, What to do, Fix action, What happens next

## 2. Architecture Boundaries

### 2.1 Domain Services (Authoritative)
- `packages/domain/` owns:
  - Financial calculations (balances, cash flow, debt, goals, independence)
  - Scenario building and simulation
  - Recommendation candidate generation
  - Recommendation validation (math, policy, freshness)
  - Evidence tracking and source hierarchy
  - Decision journal recording and replay
  - All business rule logic

### 2.2 AI Layer (Tool-Only Access)
- `packages/ai/` owns:
  - Conversational orchestration
  - Tool invocation and result assembly
  - Research workflow (when triggered)
  - Workflow classification and planning
  - Response framing and persona application
  - **Restrictions**: No financial calculations, no direct database access, no unrestricted tool calls, no financial state mutation

### 2.3 API Layer (Typed Contracts)
- `apps/api/` owns:
  - Authorization and household isolation
  - Request/response validation
  - Domain service orchestration
  - JSON serialization of typed contracts
  - **Restrictions**: No business logic duplication, no raw SQL execution for AI

### 2.4 UI Layer (Presentation Only)
- `apps/web/` owns:
  - User experience and interaction
  - Rendering of structured results
  - Approval workflows
  - Error presentation
  - **Restrictions**: No financial calculations, no data transformation, no validation logic

## 3. Financial Safety Rules

### 3.1 Money Representation
- Money is never a floating-point number
- All currency amounts are stored as integers (cents) and converted only for display
- Financial calculations use deterministic integer arithmetic

### 3.2 Calculations are Domain-Owned
- Affordability checks happen in domain services, not in AI tools
- Emergency fund rules are defined in domain services
- Financing calculations (interest, payments) are deterministic, not assumed
- Financial health status is calculated from snapshot data, not inferred by AI

### 3.3 Snapshot and Policy Versions
- Every recommendation references `financial_snapshot_id` and `policy_version` as mandatory fields
- Recommendations become stale when snapshot or policy versions change
- Stale recommendations are not delivered; audit trail explains why
- Deterministic replay from journal requires snapshot and policy identity

### 3.4 No Silent Changes
- Raw imported financial data is append-only; never silently overwritten
- Ambiguous or conflicting transactions move to Review Queue instead of failing silently
- Every financial state mutation is auditable and requires explicit source attribution

## 4. Research and Evidence

### 4.1 Research is Optional but Governed
- Research is triggered only when a current fact (interest rate, policy, provider rule) is required
- Research status (REQUIRED, PROVIDED, FAILED_CLOSED) is always tracked
- Evidence must pass source tier, freshness, and verification checks before acceptance
- Evidence relevance to claims must be verified; generic evidence does not satisfy specific claims
- If research is required but fails, the recommendation is not delivered (fail closed)

### 4.2 Source Hierarchy
- TIER_1_GOVERNMENT: Federal Reserve, IRS, SEC, FDIC
- TIER_2_PROVIDER: Issuer, regulator, official partner
- TIER_3_RESEARCH: Academic, institutional research
- TIER_4_MEDIA: News, blogs, aggregators
- Recommendations requiring TIER_1 or TIER_2 cannot use TIER_4 sources

### 4.3 Fabricated Attribution
- LLM responses must never fabricate source attribution
- If a source is named, that exact evidence must exist in the verified set
- Unsupported claims must be labeled as analysis, not fact

## 5. Validation is Independent

### 5.1 Validator Requirements
- The validator recalculates all figures and compares against recommendation figures
- The validator checks policy compliance and data freshness
- The validator identifies assumptions, risks, and sensitivity
- The validator attempts adversarial challenge: "What would make this wrong?"
- The validator surfaces warnings and failure reasons explicitly

### 5.2 Validation Status
- PASS: All checks successful
- PASS_WITH_WARNINGS: Logic correct but data is stale or assumptions are risky
- FAIL: Math error, policy violation, or required research failed
- INSUFFICIENT_INFORMATION: Cannot validate due to missing data
- Failed validation blocks normal delivery

### 5.3 Validation is Never Synthetic
- Confidence levels are calculated from data quality, research freshness, and calculation strength
- Confidence is not hardcoded or manufactured by UI code
- Validation result is returned from domain service, not constructed by UI

## 6. Current MVP Scope

### What IS in Scope
- Create household and member identities
- Add accounts and track balances
- Upload and parse financial statements (CSV, PDF, image)
- Reconcile transactions and resolve ambiguities via Review Queue
- Calculate FinancialSnapshot (cash, assets, debt, net worth, income, expenses, surplus)
- Build budgets and track against actuals
- Create and simulate scenarios (budget changes, windfalls, unexpected expenses)
- Conversational AI interface with natural language
- Generate researched recommendations (when applicable)
- Record and audit all recommendations and decisions
- Approve/decline recommendations with explanation
- Display household financial position in simple, spouse-friendly language

### What IS NOT in Scope
- Direct bank integrations (Slice 6)
- Credit card optimization (Slice 7)
- Investment advice or recommendations
- Direct money movement or transfers
- Automatic bill payment or transaction posting (without explicit review)
- Tax filing or tax optimization
- Forecasting beyond scenario simulation
- Multi-tenant deployment (single household per deployment)

## 7. Testing Requirements

### 7.1 Unit Tests
- Every financial rule requires a unit test
- Every parser requires fixtures and regression tests
- Every AI tool requires contract tests (not just "does it run")
- Domain calculations must be tested with known inputs and expected outputs

### 7.2 Integration Tests
- API contracts must be tested against real domain services
- Recommendation pipeline: intent → final recommendation
- Evidence research: query → source verification → freshness check
- Scenario simulation and accuracy
- Authorization boundaries (household isolation)

### 7.3 E2E Tests (Playwright)
- Login to recommendation delivery
- Statement upload to transaction posting
- Budget creation to scenario evaluation
- Full orchestration without mocks on the happy path

## 8. Governance

### 8.1 Code Review Checklist
Before merging:
- [ ] AGENTS.md rules are not violated
- [ ] This contract is not violated
- [ ] Financial calculations are in domain services
- [ ] No AI tool does financial logic
- [ ] Tests pass (unit, integration, E2E)
- [ ] No floating-point money
- [ ] No hardcoded financial constants (except versioned policy)
- [ ] Linting and type checking pass
- [ ] No architectural drift from approved ADRs

### 8.2 Architecture Decision Records (ADR)
All decisions affecting system boundaries, financial rules, security, or privacy require an ADR before implementation.

Current ADRs:

## 9. Red Lines (Never Allowed)

1. ❌ LLM generates balances, rates, or transaction amounts
2. ❌ Financial calculations occur in prompts or UI
3. ❌ Confidential data sent to external LLM outside privacy gateway
4. ❌ Recommendations delivered without validation passing
5. ❌ Money represented as floating-point
6. ❌ Recommendations change household state without explicit approval
7. ❌ Fabricated evidence or source attribution
8. ❌ Impersonation language in personas
9. ❌ Raw SQL execution for AI tools
10. ❌ Silent data overwrite or transaction duplication
